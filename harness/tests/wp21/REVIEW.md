# WP21 独立验收规程

WP21.1 提供独立的 `tools/review.py`、`tools/behavior.py` 与 `tools/summary.py`。具体执行命令、独立 assertions 输出格式和 PASS 硬门槛见 [Exam Ready 手册](EXAM_READY.md)。这些工具不得从候选工作树调用。

评审基于考前冻结的 cases.json 和各题卡。考生只负责实现、自测和交证据；reviewer 使用包中可信工具及工作树外的记录，实际重跑候选。此次包内没有20名考生的执行成绩。

## 一、先保留原始提交

保存候选最终源码、全部命令与失败日志、产物清单、资源锁和调度来源。原始候选不在验收阶段被“顺手修好”。发现缺陷的修复在新 attempt 或下一版工作树进行；原有失败证据保留。

运行 `manage.py scope` 检查初始化之后的实际产品差异。fixtures 中声明的初始增量不是考生修改。所有 `.cursor/`、冻结题目、harness治理、Runtime 和权威图变更都需要先识别；不能因为功能看似通过忽略超范围修改。

执行 `audit_evidence.py audit`。若材料仅有 configured_only、synthetic checkpoint、缺实际产物、hash不一致或被覆盖的旧日志，应按实际原因归类，不能直接转成通过。

## 二、在干净进程实际复跑

reviewer从相同固定基线和同题 seed 创建另一份新工作树，只应用候选产品 diff。共享模型和数据只读，结果写 reviewer自己的新 `experiment/`。不从考生提供的检查函数直接取得最终结论，也不让候选覆盖正式裁判代码。

先检查 Python 实际 `saebase.__file__`、相关模块路径和源码hash，确认运行的是候选产品代码而不是另一份 pip 安装或遮蔽模块。核对 checkpoint来源、不可变revision、tokenizer、SAE hook/层和实际文件指纹。对同一设备和数值精度使用题卡冻结容差。

逐题执行全部 positive_checks 和 negative_checks。原始实际命令应由 recorder记录。新输入只能改变同一已声明条件下的具体数值，不能新增未公开评分要求。需要模型的正例使用真实权重；错误输入的早拒绝测试可以在加载之前完成，并检查没有产生 completed 结果。

## 三、按任务类型核验行为

| 类型 | 独立检查重点 |
| --- | --- |
| 参数或计算修改 | 同一输入对照默认与变更值，独立由保存的数组重算输出；确认参数到达真实算法而不只是YAML |
| Dataset新增 | 从配置/registry走到reader与真实任务消费，核对样本ID、group/split、去重和非法输入；清单出现名称不足以通过 |
| Model新增 | 原有未注册的真checkpoint，实际构造、前向、激活捕获、identity patch；核对新架构适配与旧模型回归 |
| 组件删除 | 固定seed先前实际可用；候选在新进程中不再发现或执行旧ID；默认组件仍能运行；旧数据/权重/结果hash保持 |
| Task/Subtask | 同一Registry/Runner真实分派；subtask selector和task.path分别检查；未知值拒绝，原有默认分支保持 |
| 参数搜索 | 复算网格笛卡尔积和trial身份，逐项检查真实子运行、失败记录、有选优目标时的选优/tie-break与独立确认输入；纯枚举/恢复题按冻结范围检查 |
| 中断恢复 | 人为停止已公开的边界，保存旧成功/失败产物hash；新进程恢复只运行缺项、身份冲突拒绝，不清空旧leaf |
| 小训练 | trainer实际收到seed与1024-token预算，权重确实变化且可重载；同seed容差与不同seed比较按题卡，不要求训练提升 |
| 文件完整性 | 对真实run篡改单个字节、遗漏/增加文件，核验清单发现；canonical配置身份区分原Runtime YAML hash |
| 归档清理 | 遍历、绝对路径、symlink和外部sentinel负例；解包到新目录，损坏归档拒绝；仅处理明确所有权文件 |
| 多阶段集成 | 上游产物hash与下游消费身份对应，中间失败阻止后续“完成”，恢复使用新attempt，原始失败仍可审计 |

每题具体数值、范围、公式和必交文件以题卡为准。本表只说明如何独立取得证据。

## 四、评分和状态

每题100分，分为真实功能40、兼容及负例25、证据与可复现20、范围与文档15。评分项须引用对应题卡检查和实际日志。通过需要全部硬条件满足，分数用于记录部分完成程度，不能用文档分补足缺失的真实运行。

以下情况保持非PASS并写明原因：真实checkpoint正例未完成；冻结核心功能失败；虚构/替换执行结果；更改评分标准；越权改治理/Runtime；删除他人或历史证据；因环境缺失而未运行。环境阻塞使用 `ENV_BLOCKED`，不自动解释成候选实现错误。

建议最终记录包含 case_id、run_id、原基线/初始化/候选SHA、逐项检查结果与日志、分项分数、结论、六类失败归因、owner、stage、复现命令及未解决事项。不要填造人类姓名或批准；自动技术验证与最终人类审阅保持各自身份。

## 五、把测试发现用于改进 Harness

先在原基线复现，区分既有产品缺陷和候选引入问题。规则缺口与评分器漏检由治理维护者修复；考生不负责改规则让题目通过。新需求记为 `EVALUATOR_SCOPE_GAP`，进入后续版本。保留本轮冻结标准、原始结果和所有失败，再用新的同类任务检查修订能否泛化。
